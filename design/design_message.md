# 前言

一个好的聊天软件，不仅需要的是稳定的连接，高耐受的服务器架构，优美简约的前端设计，丰富有趣的功能体验，以及基本的应有的聊天功能，或者说，作为一个软件本身就应该有的功能，都具备，才算是一个优秀的合格的聊天室。在完成好了昨天服务器传输端的架构之后，下面开始进行业务层的拆分和构思。

## 总体拆分

目前就聊天室的整体来说，可以拆分成三个大的部分：业务层，传输层，存储层。

1. 业务层：包括登录功能，聊天功能，好友功能，群组功能，动态功能等。
2. 传输层：即使用io_uring技术，以Proactor模型 + 线程池分发的混合模型为架构，所搭建的网络传输层。
3. 存储层：采用MySQL + Redis双存储，MySQL存储永久信息，Redis存储实时信息。

## 业务层详细拆分

1. 消息解析器：在on_recv_的回调函数内，先检查是来自客户端什么样的数据，是账号模块，还是好友模块，还是聊天模块......
2. 数据库查询器：之后在检查好之后，检查本地是否有登录记录，如果没有登录记录，则重新登录，如果有登录记录，则直接自动登录。登录成功之后，检查是否有本地记录，如果有本地记录，则直接同步，没有的话就从服务端拉取。其实还有很多，但主要是进行核对和查询。
3. 消息分发器：具体分为账号模块，好友模块，聊天模块，群组模块，动态模块。
- 账号模块：  
  - 实现登录、注册、注销
    实现数据加密
    实现通过验证码登录/注册/密码找回（邮件/手机号等）（提高）

- 好友模块：  
  - 实现好友的添加、删除、查询操作
    实现显示好友在线状态
    禁止不存在好友关系的用户间的私聊
    实现屏蔽好友消息
    实现好友间聊天

- 群组模块：
  - 实现群组的创建、解散
    实现用户申请加入群组
    实现用户查看已加入的群组
    实现群组成员退出已加入的群组
    实现群组成员查看群组成员列表
    实现群主对群组管理员的添加和删除
    实现群组管理员批准用户加入群组
    实现群组管理员/群主从群组中移除用户
    实现群组内聊天功能

- 聊天模块：
  - 实现查看历史消息记录
    实现用户间在线聊天
    实现在线用户对离线用户发送消息，离线用户上线后获得通知
    实现在线发送文件
    实现在线用户对离线用户发送文件，离线用户上线后获得通知/接收
    实现用户在线时,消息的实时通知
    收到好友请求
    收到私聊
    收到加群申请
    实现文件发送的断点续传

对于消息解析器和数据库查询器，我都想设计成两个类，然后在类内设计一个可以查询的方法，用这个方法查询完给的消息之后，直接根据消息编码来填充message，这个消息编码代表了是什么模块的内容，但这里可以前期指定一下，具体哪个模块对应哪个消息编码，之后用这个消息编码，和当前用户的状态，来综合进行数据库的查询，查询完成之后，把查询结果保存下来，然后放入到消息分发器内，进行分发。

总结就是：消息解析器进行消息的解析，看看到底是哪个模块的内容；数据库查询器综合当前用户的状态，和消息编码，进行数据库的查询，然后把查询的结果保存下来，供给消息分发器；消息分发器进行消息的分发，具体到某个什么什么部分。

## 7月22日开发总结

今日主要是先对整体的项目重新进行了拆分，分成了业务层，传输层和存储层。而今天对业务层主要进行了构建。

消息解析器：用来解析对应的消息内容，具体到什么什么模块。
消息类型和消息编码：想要解析好每个消息内容，就应该先提前设计好，不同的消息类型，与之对应的消息编码。我采用枚举的方式，以间隔段落的形式来处理不同的消息内容。
数据库查询器：根据当前消息的类型，以及当前用户的状态，来返回查询的结果。这个结果最后要供给消息分发器来进行消息的精准分发。
消息分发器：将数据库查询器查询到的内容，对应到不同类型的消息，然后进行真正的消息处理。
