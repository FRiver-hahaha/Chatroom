# 前言

在设计整个聊天室的过程中，需要将不同设计的模块进行拆分，前端和后端，而在后端部分，主要需要拆分的部分又有客户端和服务端，而设计一个好的联网软件，首先要设计好服务端的架构，以下是我对服务端设计的思路。

## io_uring

本次设计我将采用io_uring，这是一个较为前沿的技术，要求linux内核版本在5.1以上，他的好处在于：  

1. 具有极低的性能开销。
2. 有全新的生产者——消费者设计模型，分为两个队列，提交队列和处理队列，内核态用户态切换可达到常数级别。

## io_uring的使用

1. 初始化io_uring，会初始化两个队列，提交队列和完成队列。
2. 创建监听socket。
3. 进行第一次的accept连接，即对以后的accept连接请求进行处理。
4. 进行第一次的心跳检测。
5. 等待cqe，分多种情况批量处理cqe，如果是accept，接受连接；如果是recv，处理消息；如果是send，继续下一个请求；如果是timeout，执行心跳检查。
6. 填充sq
7. 关闭并且清理

## 补充建议

1. 为 io_uring 启用 IORING_SETUP_SQPOLL 标志，让内核主动轮询sq，极大提高了io的效率。
2. 设置socket的时候，要设置SOCK_NONBLOCK非阻塞模式。
3. 使用multishot 模式的 accept(io_uring_prep_accept_multishot)，提交一次就可以为每个连接生成cqe。

## 7月21日开发总结

一开始并没有什么思路，由于之前我做了一个简单的规划，所以还算有些想法。

对于服务器的底层架构，我选择的是io_uring，这是Linux前沿版本的新技术，比传统的epoll开发，更能榨干硬件性能。

经过简单的io_uring的学习，我了解了一些基本原理：  
1. io_uring通过提前调整参数，可以设置好cpu的空闲休眠时间，以及内核的处理模式，分有主动轮询和非主动轮询以及其他模式。
2. io_uring正如其名，通过维护一个"环"，来完成高效的事件处理。
3. 主要是维护两个队列，sq和cq，分别是提交队列，和完成队列，程序只需要把任务提交给sq，sq在提交到一定程度之后，统一发送给内核态，内核态进行处理，之后切换回用户态，把结果放入cq中，再在cq中获取结果。  

下面是具体的服务端网络架构的代码思路：

1. 创建server类，配置好listen_fd_，服务器开启标志，线程池对象，回调函数，客户端连接对应表等。
2. 创建connection结构体，存储好各个客户端的用户信息，包括socket，缓冲区，发送队列等。
3. 先创建对象，然后初始化服务器，包括初始化uring，初始化socket等一系列配置。之后完成第一次的接受连接，可以让以后自动进行连接，还有第一次的timeout时间处理。
4. 之后在服务器内，主要是通过一个事件循环，对cq进行检查，创建新的cqe，然后处理这个cqe，之后回收cqe，继续执行，在之后通过批量非阻断的方式处理cqe之后，统一提交一次sq。这里要注意，提交sq的次数要注意，这决定了整个服务器的性能。
5. 之后进入到handle_cqe的函数中，对于不同的cqe，需要进行区分，这里有4个大类，为接受连接的accept，处理接受消息的recv，处理发送消息的send，处理时间检查的timeout。在面对sqe无法申请成功的情况时候，这说明，现在的sq队列已经满了，需要提交一次sq，但实际上，除了accept，其他的都直接return就可以，而accept如果没有创建成功，就可以提交一次，因为如果对每个类型的cqe都进行一次提交，这样就违背了本身具有极高效率的io_uring的设计模式，但又因为,accept这种行为，本身只是在客户端建立连接这一次，频率很低，所以这样的开销是值得的。至此，整个ring，两次的submit全部被用完了。还有一点，accept在完成之后，进入的并不是submit_accept，其他的三个都是各自本身，accept对应的是recv，因为一个已经建立好连接的c/s需要进行一次消息的发送，否则之后就无法发送消息了。
6. 在处理各个部分的内容时，我这里由于之前写过一个高效的线程池，所以我拿来考虑，决定把各个cqe的处理内容，放入到多个固定数量的线程中，可以提高效率。所以至此，整个服务器的架构，它具有了主从reactor的分发模式，也具有proactor模型的队列填充，这是一个混合型的服务器架构。
7. 回调函数是对未来服务器业务部分设计的基石。通过function包装，以后在使用回调函数的时候，只需要在server对象中注册一次回调函数，在回调函数去执行，对应类型的，会对全体用户有统一显示的内容，我拿微信举例，比如，收到消息，让用户显示红点，显示发送消息的时间，并且在用户列表中置顶等基础操作。这样的功能只需要在后续，业务层级开发的时候直接使用就好，回调函数的设计，使用了std::move，可以直接把所有权转移给on_connect_等，然后在服务端检查到回调函数的时候，执行内容。
8. io_uring本身是线程安全的，但是多线程内处理的时候，一些其他资源并不是线程安全，但为了最好不用锁，这里大模型给我了个好的解决方案，可以使用一个消息队列，即让他们先放入到消息队列，子线程放入，主线程取出。
9. 目前看来是没什么问题了，剩下的内容就是服务器的关闭。但其实还有个关键问题，为什么事件循环先去处理cqe。明明cqe是完成事件的内容，应该是先提交sqe到sq内，然后通过处理之后，放入到cq内，对cq进行处理。这样听起来是这样的，但是如果顺着下来，就无法形成循环。因此第一次的cqe检查，是空处理的，之后待用户态放入sqe到sq之后，经过内核态处理到cq内，才会执行。
10. 其实还是有很多细节的，比如，怎么去标识每个sqe对应了每个客户？这里是使用了一个指针，在sqe提交之后，有个指针会描述整个客户端，会把他放入到sqe的user_data中，用于标识，在cqe中检查的时候，进行查看。还有，先进行用户标识，还是先进行sqe的内容上传？按代码风格来说，先进行上传更有鲁棒性，但实际上，两者独立，前后顺序无关。

至此，服务端的网络连接大功告成，也就是说，服务端的网络连接部分已经完成，并且提供了回调函数的处理接口，以及性能高效，可以发挥到极致。明日将开始服务端的业务态详细分层和部分处理。
